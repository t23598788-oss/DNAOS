## Responsibility Separation (DNA OS Engineering Principle, owner 2026-07-14, DNA-000054)
- **Human** decides **WHY** — Vision, Business Goals, Policy, Architecture Direction, Constraints, Business Rules
- **Runtime** decides **WHAT is required** — Architecture Integrity, Module Relationship, Dependency, Runtime Health, Validation, Knowledge, Self Diagnosis, Self Explanation
- **AI** decides **HOW to implement** — Analysis, Refactoring, Repair, Optimization, Knowledge Assimilation, Capability Expansion
- **Validation** decides **WHETHER it is correct**
- **Deployment** occurs only after Validation PASS — Runtime is the final authority for technical integrity, Human is the final authority for business intent

### Local-AI Pipeline Responsibility Split (owner, 2026-07-25 — "แยกผู้รับผิดชอบแต่ละหน้าที่สิ")
Root cause found live same day: `ANTHROPIC_API_KEY` was never actually set as a Supabase secret (`supabase secrets list` had no such key) — every Claude call inside `supabase/functions/line-webhook-v2` (document classification, tool routing, conversational fallback) had been silently returning null since it was built, never actually working in production. Owner has no cloud AI budget and chose local-only processing over buying a key ("ย้ายทุกอย่างมาประมวลผลในเครื่อง Mac"). This split each piece's job cleanly instead of one thing trying to do everything:
- **Cloud (`supabase/functions/line-webhook-v2`)** — receives real LINE events, does deterministic non-AI work synchronously (payment-info requests, debt-followup acks, payment claims, print-job quick-reply postbacks), and for anything that needs real thinking, only **enqueues** a row in `ai_tasks` (`supabase/migrations/20260725000006_ai_tasks.sql`) and returns. Never calls a cloud LLM directly anymore in the live path.
- **Cloud (`supabase/functions/ai-callback`)** — deliberately "dumb wiring only," zero LLM calls. Takes an already-computed AI result posted from the owner's Mac and does the real, unchanged business logic (`engines/process-classified-image.ts`, `receipt_documents`/`print_jobs` writes, `tryAutoConfirmPayment`) and the LINE push. Auth via `AI_CALLBACK_SECRET` shared secret, same pattern as the existing cron endpoints.
- **Local (`~/dna-os-ollama/ai-task-watcher.mjs`, on the owner's own Mac)** — does 100% of the actual AI thinking: polls `ai_tasks`, classifies document photos via Ollama vision (`qwen2.5vl:7b`, prompt kept in sync by hand with `ocr-classify.ts`) and drafts conversational replies + updates per-customer behavioral memory via Ollama text (`thawatchai`, prompt kept in sync with `thoughtful-fallback.ts`/`customer-memory.ts`), then POSTs the result to `ai-callback`. Runs independent of any Claude/chat session, same pattern as `print-watcher.mjs` (physical printer) and `watch-drive.mjs` (Google Drive ingestion) — cloud genuinely cannot reach a process on a home WiFi network, so this bridge direction (local polls cloud, not the reverse) is required, not a choice.
- **LaunchAgents** (`com.dnaos.*.plist` in `~/dna-os-ollama/`) — the actual persistent runtime for every local watcher above. Claude Code's own safety classifier blocks autonomous `launchctl load`/background-daemon starts — installation is always a 2-line command the owner runs himself once; not yet confirmed installed for `ai-task-watcher` as of this entry.
- Known gap, stated honestly: only the image-classification and final-text-fallback AI touchpoints are converted to this pipeline so far. `tool-router.ts` (debt/order-status/purchase-history routing) and `auto-build-event.ts` (building a material quote from free text) still call the dead Claude path and silently return null — pre-existing gap, not newly introduced today, needs the same local-AI conversion in a follow-up pass.

### Volume (คิว) ↔ Weight (ตัน) Conversion Rule (owner, 2026-07-26)
คิว (m³) is a **volume** measurement (width × length × height); ตัน is a **weight** measurement (a real scale reading). They are only convertible through a material's own density: `น้ำหนัก(ตัน) = ปริมาตร(คิว) × ความหนาแน่น(ตัน/คิว)` — **never hardcode one conversion factor across all materials.** Real density varies by (1) the material's intrinsic specific gravity (steel ~7.85, silica/limestone ~2.65, wood/brick 0.6–1.8 ton/m³ for the solid substance itself), (2) void ratio between grains/particles (graded crushed rock packs tighter than uniform-size screened stone), and (3) moisture content (wet sand/soil is 10–20% heavier than dry). `material_types.density_ton_per_cbm` (migration `20260726000002_material_density.sql`) holds the real value per material — populated for all 11 real materials from the owner's own engineering reference figures (steel 7.85, ready-mix concrete 2.40, หินคลุก 1.70, ทรายละเอียด 1.50, ทรายหยาบ 1.45, หิน 3/4 and similar graded stone 1.425, ดินถม/ลูกรัง 1.30 — never guessed, this exact table came from the owner). `supabase/functions/line-webhook-v2/engines/material-density.ts` — `cbmToTon()`/`tonToCbm()` do the real conversion, `validateDensity()` sanity-checks a value against physically plausible bounds (must be > 0.3 and < 8 ton/m³ — catches an obviously-wrong entry like "sand density 7.8" or "steel density 1.2," not a strict business rule).
Real gap found the same day as the pricing rewrite: `vehicle_types.load_capacity` for "รถพ่วง (ดั้ม)" was stored as 22 (a คิว figure) when the real standard trailer capacity the owner actually quotes is 30 ตัน — fixed live in the database (not hardcoded in code) since load_capacity is meant to be read in ตัน throughout the pricing engine after the 2026-07-26 unit-standardization.

## Recommendation & Approval Levels (ระดับของข้อเสนอแนะและการอนุมัติ)

ทุกแผนการทำงาน (Execution Plan) ที่เสนอโดย Worker จะถูกจัดระดับและจัดการดังนี้:

*   **LEVEL 1: Informational (แค่แจ้ง)**
    *   การเปลี่ยนแปลงเล็กน้อยที่ไม่มีผลกระทบ (เช่น แก้ไขเอกสาร) Runtime จะบันทึกและดำเนินการต่อ

*   **LEVEL 2: Recommended (แนะนำ)**
    *   การแก้ไขที่ปลอดภัย (เช่น Refactor) Runtime จะอนุมัติให้ดำเนินการได้โดยอัตโนมัติ

*   **LEVEL 3: High Impact (ควรตรวจสอบก่อน)**
    *   การเปลี่ยนแปลงที่อาจกระทบหลายส่วน (เช่น เปลี่ยน API) Runtime จะทำการวิเคราะห์ผลกระทบ (Impact Analysis) และเสนอแผนการดำเนินงานเพื่อรอการตรวจสอบ

*   **LEVEL 4: Approval Required (ต้องขออนุมัติ)**
    *   การเปลี่ยนแปลงที่มีความเสี่ยงสูง (เช่น ลบโมดูลหลัก) Runtime จะเสนอเรื่องให้มนุษย์ (CEO) อนุมัติผ่าน Dashboard เท่านั้น

*   **LEVEL 5: Forbidden (ห้าม)**
    *   การกระทำที่ขัดต่อ Constitution (เช่น ลบฐานข้อมูล, สร้างโมดูลซ้ำ) Runtime จะปฏิเสธและหยุดการทำงานทันที

## Architecture Principles (หลักการสถาปัตยกรรม)

1.  **Constitution**: คือกฎหมายสูงสุดของระบบ เขียนและแก้ไขโดยมนุษย์เท่านั้น
2.  **Runtime**: คือผู้บังคับใช้กฎของ Constitution ไม่ใช่ AI และเป็นกลาง ไม่ขึ้นกับ AI ค่ายใด
3.  **Governance Engine**: เป็นส่วนหนึ่งของ Runtime ทำหน้าที่อ่าน Constitution, Registry, และ Repository เพื่อตัดสินผลตามกฎที่มีอยู่เท่านั้น ไม่มีสิทธิ์คิด, ตีความ, หรือแก้ไขกฎ
4.  **External Workers**: AI ทุกตัว (Gemini, Claude, GPT, etc.) เป็น "คนงานภายนอก" ที่รับ Task ไปทำ แล้วส่งผลกลับมาให้ Runtime ตรวจสอบ
5.  **Chain of Command**: Worker → Runtime (Governance Engine) → Human (CEO). Runtime เป็นผู้อนุมัติ, ปฏิเสธ, หรือส่งต่อให้มนุษย์ตาม Constitution เท่านั้น
